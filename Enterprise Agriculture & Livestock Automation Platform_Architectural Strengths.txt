Aggregate Roots: Act as gateways to the entities inside the aggregate boundary. All database operations (load, save, update) must be performed through the Aggregate Root.
Entities: Objects with distinct identities that persist over time.
Value Objects: Immutable objects with no identity defined solely by their attributes (e.g., money amount and currency, or weight value and unit). Value objects prevent side effects by ensuring that modifications return a new instance rather than modifying the existing state in place.

// Example Value Object implementation representing money/currency
public abstract class ValueObject
{
    protected abstract IEnumerable<object> GetEqualityComponents();
    public override bool Equals(object? obj)
    {
        if (obj == null || obj.GetType() != GetType()) return false;
        var other = (ValueObject)obj;
        return GetEqualityComponents().SequenceEqual(other.GetEqualityComponents());
    }
    public override int GetHashCode()
    {
        return GetEqualityComponents()
            .Select(x => x != null ? x.GetHashCode() : 0)
            .Aggregate((x, y) => x ^ y);
    }
}

        if (amount < 0) throw new ArgumentException("Amount cannot be negative.");
        Amount = amount;
        Currency = currency ?? throw new ArgumentNullException(nameof(currency));
    }
    protected override IEnumerable<object> GetEqualityComponents()
    {
        yield return Amount;
        yield return Currency;
    }
}

Step 6: Bounded Contexts
In Domain-Driven Design (DDD), complex systems are divided into logical boundaries called Bounded Contexts. Each Bounded Context has its own language (Ubiquitous Language), domain model, database schema, and micro-services boundaries.

6.1 Defined Bounded Contexts
We divide AgriERP into six primary Bounded Contexts:

Bounded Context	Ubiquitous Language Core Terms	Database Schema	Primary Responsibility
Identity & Access Management (IAM)	User, Role, Permission, Tenant, Grant	iam	Authentication, OAuth2 tokens, tenant scoping, and authorization filters.
Livestock Management	Animal, Tag, Breed, Sire, Dam, Treatment, MilkYield	livestock	Animal registrations, veterinary logs, breeding cycles, and milk/egg production records.
Crop & Precision Ag	Field, Zone, CropCycle, IrrigationValves, NPK	crop	Field mapping, seed sowing, automated watering schedules, sensor ingestion, and fertilizer plans.
Supply Chain & Inventory	StockItem, Batch, Lot, ReorderLevel, PO, Dispatch	inventory	Raw material purchases, grain/feed warehouse tracking, expiry flags, and outbound distribution.
Financials & Accounting	ChartOfAccounts, GL, JournalEntry, Debit, Credit	finance	General ledger postings, asset depreciation, tax computations, and accounts reconciliation.
HR & Payroll	Laborer, Shift, TaskRate, PaySlip, Benefit	hr	Seasonal workforce timesheets, piece-rate payroll, and labor contracts.
6.2 Context Mapping & Relationships
Bounded Contexts do not exist in isolation; they must communicate. We map their relationships using established DDD patterns:

Upstream/Downstream (U/D): The upstream context changes independently, affecting the downstream context.
Customer-Supplier (C/S): A subset of U/D where the upstream team must coordinate with the downstream team's needs.
Shared Kernel (SK): A subset of the model shared between contexts (e.g., core multi-tenant primitives). We minimize this to keep modules independent.
Anti-Corruption Layer (ACL): A translation layer in the downstream context that shields its domain model from upstream changes.
Open Host Service (OHS) / Published Language (PL): The upstream context provides a public API and standard data exchange format (JSON/XML).

The Write Path (Commands):
API Controller receives a POST/PUT/DELETE request and sends a command to MediatR.
MediatR runs the request through the ValidationBehavior pipeline to enforce syntactic checks.
The Command Handler loads the aggregate root from the database via EF Core.
The aggregate root executes domain logic, validates business invariants, mutates state, and registers domain events.
The DbContext writes the changes to SQL Server in a single transaction.
The Read Path (Queries):
API Controller receives a GET request and sends a query to MediatR.
The Query Handler bypasses EF Core change tracking entirely.
It uses Dapper to run optimized, read-only SQL queries directly against SQL Server read-replicas.
The query returns simple Data Transfer Objects (DTOs) mapped directly from the database, maximizing performance and reducing memory overhead.
7.3 Outbox Pattern for Reliable Eventual Consistency
To ensure reliable, transactional cross-module communication without distributed transactions (which cause locking and scale bottlenecks), we use the Outbox Pattern:

mermaid
sequenceDiagram
    participant App as Application Handler
    participant DB as SQL Server Primary
    participant Outbox as Outbox Processor (Worker)
    participant Broker as Event Broker (RabbitMQ)
    App->>DB: 1. Modify business data (e.g., slaughter animal)
    App->>DB: 2. Write Outbox Message (e.g., AnimalSlaughteredEvent)
    DB->>DB: 3. Commit SQL Transaction atomically
    Outbox->>DB: 4. Poll database for pending outbox messages
    Outbox->>Broker: 5. Publish message to RabbitMQ / Service Bus
    Outbox->>DB: 6. Mark message as processed in database
Guaranteed Delivery: Business state modification and event logging are performed inside the same ACID database transaction.
Resiliency: If the message broker is offline, the Outbox Processor retries processing, ensuring at-least-once delivery of integration messages.
7.4 Caching Topology with Redis
We use Redis as our distributed caching layer to reduce pressure on SQL Server:

Session & Authorization Cache: User roles, active permissions, and tenant configurations are cached in Redis under the prefix auth:tenant:{tenantId}:user:{userId}. The system only hits SQL Server for permission checks when this cache expires.
IoT Cache (Hot Path): Telemetry values are written to Redis (iot:sensor:{sensorId}:latest) at ingestion time. Dashboard queries pull from Redis, bypassing the database.
Cache Invalidation Strategy:
Time-to-Live (TTL): Dynamic cache expiration matching the update frequency of the resource (e.g., 20 minutes for system settings).
Explicit Eviction: Handlers evict related cache keys when commands mutate state (e.g., updating user permissions evicts the user's cache key).

Step 9: Database Design
The database architecture is built on SQL Server Enterprise, using a Single Database with Logical Schema & Row-Level Multi-Tenant Isolation strategy.

9.1 Multi-Tenant Isolation & Schema Strategy
To isolate tenant data safely and prevent performance bottlenecks:

Schema Partitioning: Tables are grouped into database schemas matching the Bounded Contexts: auth, livestock, inventory, crop, finance, and hr.
Row-Level Tenancy (IMultiTenant): Every table containing business data has a TenantId UNIQUEIDENTIFIER column.
Composite Unique Keys: Any standard unique constraints (e.g., animal tag numbers, employee numbers) are defined as composite keys containing the TenantId (e.g., unique index on TenantId, TagNumber). This allows different tenants to have overlapping tag names without constraint violations.
Tenant Filtering: Standard queries use an EF Core Global Query Filter: entity.HasQueryFilter(e => e.TenantId == CurrentTenantId).

11.3 Multi-Tenant Interceptor Pattern
To ensure that the correct tenant context is sent with every single backend request, we register a global HttpInterceptorFn. This interceptor automatically injects the tenant ID into the headers:

typescript
import { HttpInterceptorFn } from '@angular/common/http';
import { inject } from '@angular/core';
import { TenantService } from '@agri-erp/core/tenant';
export const tenantInterceptor: HttpInterceptorFn = (req, next) => {
  const tenantService = inject(TenantService);
  const activeTenantId = tenantService.getActiveTenantId();
  if (activeTenantId) {
    const clonedRequest = req.clone({
      headers: req.headers.set('X-Tenant-Id', activeTenantId)
    });
    return next(clonedRequest);
  }
  return next(req);
};

12.2 Optimized Permission-Based Security Flow (Redis Caching)
In our review of your current code structure, we identified that 

PermissionFilter.cs

12.3 Backend Permission Filter Implementation
Below is the optimized, high-performance PermissionFilter implementation utilizing Redis caching:

csharp
using Microsoft.AspNetCore.Mvc;
using Microsoft.AspNetCore.Mvc.Filters;
using StackExchange.Redis;
using System.Security.Claims;
using System.Text.Json;
namespace AgriERP.Modules.Auth.Presentation.Authorization
{
    public class PermissionFilter : IAsyncAuthorizationFilter
    {
        private readonly string _requiredPermission;
        private readonly IConnectionMultiplexer _redis;
        private readonly IAuthDbContext _context;
        public PermissionFilter(string requiredPermission, IConnectionMultiplexer redis, IAuthDbContext context)
        {
            _requiredPermission = requiredPermission;
            _redis = redis;
            _context = context;
        }
        public async Task OnAuthorizationAsync(AuthorizationFilterContext context)
        {
            var user = context.HttpContext.User;
            if (!user.Identity?.IsAuthenticated ?? true)
            {
                context.Result = new UnauthorizedResult();
                return;
            }
            var userId = user.FindFirst(ClaimTypes.NameIdentifier)?.Value;
            var tenantId = user.FindFirst("tenant_id")?.Value;
            if (string.IsNullOrEmpty(userId) || string.IsNullOrEmpty(tenantId))
            {
                context.Result = new UnauthorizedResult();
                return;
            }
            var db = _redis.GetDatabase();
            string cacheKey = $"auth:tenant:{tenantId}:user:{userId}:permissions";
            // 1. Redis Cache Lookup
            var cachedPermissions = await db.StringGetAsync(cacheKey);
            List<string>? permissions;
            if (cachedPermissions.HasValue)
            {
                permissions = JsonSerializer.Deserialize<List<string>>(cachedPermissions!);
            }
            else
            {
                // 2. Cache Miss: Read DB and write back to Redis (TTL 15 min)
                permissions = await _context.UserRoles
                    .Where(ur => ur.UserId == Guid.Parse(userId))
                    .Join(_context.RolePermissions,
                        ur => ur.RoleId,
                        rp => rp.RoleId,
                        (ur, rp) => rp.PermissionCode)
                    .Distinct()
                    .ToListAsync();
                await db.StringSetAsync(cacheKey, JsonSerializer.Serialize(permissions), TimeSpan.FromMinutes(15));
            }
            // 3. Verify Permission
            if (permissions == null || !permissions.Contains(_requiredPermission))
            {
                context.Result = new ForbidResult(); // 403 Access Denied
            }
        }
    }
}

14.3 Enterprise Database & Persistence Scaling
Transactional SQL Server: Deployed in a multi-subnet configuration using Always On Availability Groups. A primary replica handles all write commands, and two read-only replicas scale read queries via dynamic load balancing.
Telemetry Data (InfluxDB / TimescaleDB): Deployed as a multi-node cluster partition. Old partitions are compressed into read-only files to minimize hard-drive storage overhead.
Message Broker (RabbitMQ): Deployed using the RabbitMQ Cluster Operator on Kubernetes. Enforces mirrored queues across availability zones to guarantee message persistence during outbox processing.
